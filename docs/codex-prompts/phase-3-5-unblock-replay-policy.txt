DESBLOQUEO FASE 3.5 — REPLAY EXACTO Y TRAZABILIDAD DE StabilityPolicy

La detección del bloqueo es válida.

La especificación v1.1 exige para 3c–3.5 `plan_evaluations` con modo y resumen embebido, y permite que versiones de algoritmo/política y otros datos de trazabilidad residan en columnas estructuradas sin crear tablas de auditoría normalizadas. También establece que una nueva capacidad que lo necesite puede introducir una migración probada y proporcional.

Por tanto se AUTORIZA una ampliación mínima del schema para resolver exclusivamente este gap.

No confundir con:

- TdeePolicy.version;

estimatorStabilityPolicyVersion DEBE provenir directamente de:

No inferir desde TDEE.
No parsear evidenceKey.

==================================================
3. COMPATIBILIDAD CON FILAS LEGACY v4
==================================================

NO fabricar la StabilityPolicy histórica de filas ya existentes.

Por esa razón, la columna física de MIGRATION_4_5 debe ser nullable para registros legacy, por ejemplo:

estimatorStabilityPolicyVersion TEXT NULL

El modelo de dominio puede representar esta ausencia explícitamente.

Regla:

- evaluaciones nuevas creadas por el flujo prospectivo de Fase 3.5: valor obligatorio/no nulo;
- evaluaciones migradas desde v4: null si no existe evidencia estructurada inequívoca.

NO rellenar las filas antiguas con "stability-v1" solo porque sea el valor por defecto actual.

NO reconstruirlo informalmente desde evidenceKey.

Una fila legacy con valor null:

- se conserva;
- sigue siendo visible históricamente;
- NO se considera replay exacto reproducible;
- debe producir una razón/estado explícito de input de replay incompleto;
- no puede hacer que el criterio de reproducibilidad se considere MET.

Esto evita inventar historia y permite que las nuevas evaluaciones prospectivas sí sean plenamente reproducibles.

==================================================

==================================================

Implementar migración no destructiva 4 -> 5.

Debe:

- preservar todas las tablas y filas existentes;
- añadir únicamente el campo estructurado necesario a plan_evaluations;
- no crear tablas;
- no borrar ni reescribir evaluaciones históricas;
- dejar null para filas legacy sin valor estructurado conocido.

Registrar:

MIGRATION_1_2
MIGRATION_2_3
MIGRATION_3_4
MIGRATION_4_5

No usar fallback destructive migration.

Añadir test real de migración 4 -> 5.

Verificar:

- datos v4 preservados;
- columna nueva presente;
- fila legacy mantiene null;
- ninguna tabla nueva inesperada;
- adjustment_proposals sigue sin existir.

==================================================
6. REPLAY EXACTO
==================================================

Una evaluación es candidata a replay exacto únicamente si todos los inputs imprescindibles están disponibles estructuralmente.

Para estimator stability, exigir:

estimatorStabilityPolicyVersion != null

Si es null:

NO asumir valor.
NO parsear evidenceKey.
NO declarar replay determinista exitoso.

El reporte debe distinguir, con estado o motivo estructurado equivalente:

REPLAY_INPUT_INCOMPLETE
LEGACY_STABILITY_POLICY_UNKNOWN

o nomenclatura equivalente clara.

Las evaluaciones prospectivas nuevas deben ser replayables con la versión real persistida.

==================================================
7. CRITERIOS DE VALIDACIÓN
==================================================

La existencia de filas legacy no invalida automáticamente toda la Fase 3.5.

Pero esas filas:

- no pueden satisfacer por sí solas el criterio de replay exacto;
- no pueden convertir reproducibilidad a MET;
- no deben contarse como evidencia prospectiva nueva;
- pueden permanecer como contexto histórico visible.

La ventana personal de Fase 3.5 debe acumular nueva evidencia prospectiva con observabilidad suficiente.
