2. REPLAY DE VENTANA DESLIZANTE NECESITA MEMORIA INICIAL
==================================================

Defecto actual:

El reporte selecciona las últimas 28 fechas evaluables, pero ShadowReplayEngine empieza siempre con memory = null.

Si el plan tiene historia anterior a windowStart, la primera evaluación de la ventana pudo depender legítimamente de DecisionStateMemory previa. Un replay que empieza en null no reproduce exactamente esa evaluación.

No ampliar la ventana personal de 28 días.

Separar:

A. ventana de VALIDACIÓN:
- sigue siendo las últimas 28 fechas evaluables del plan actual;
- no cambia.

B. contexto de REPLAY:
- debe disponer de la memoria inicial correcta justo antes de windowStart.

Implementar una solución mínima equivalente a:

ShadowReplayEngine.replay(
    items,
    initialMemory,
    expectedMemory
)

Semántica:

- initialMemory = reconstrucción determinista de las revisiones vigentes del MISMO plan anteriores estrictamente a windowStart;
- si no existe historia previa, initialMemory = null;
- el replay arranca desde initialMemory, no siempre desde null;
- expectedMemory = memoria persistida real del plan.

Para que la memoria final pueda compararse con la memoria persistida actual:

- los replay items deben incluir las revisiones vigentes del plan desde windowStart hasta la última evaluación vigente del plan, incluyendo evaluaciones no evaluables/INSUFFICIENT_DATA posteriores al último día evaluable si existen;
- esto NO aumenta evaluableDays ni cambia windowStart/windowEnd del reporte;
- solo proporciona contexto exacto de replay.

No mezclar planes.
No usar filas obsoletas de una misma fecha.

Añadir tests:

RW-01
Plan con >28 días donde la primera fecha de la ventana depende de una confirmación anterior a windowStart -> replay MATCH usando initialMemory.

RW-02
Mismo caso empezando artificialmente desde null -> no debe aceptarse como equivalente.

RW-03
Existe una evaluación INSUFFICIENT_DATA posterior al último día evaluable y modifica la memoria persistida -> el replay incluye ese contexto y termina igual a la memoria persistida.

3. TDEE STABLE: CONTAR SOLO FECHAS REALMENTE EVALUADAS
==================================================

Defecto actual:

ShadowValidationAnalyzer cuenta cualquier TdeeEstimate dentro del span civil de la ventana.

La regla normativa es:

TDEE STABLE en al menos 7 fechas EVALUADAS distintas.

Una fecha con TDEE pero sin PlanEvaluation seleccionada NO puede sumar una confirmación de estabilidad para este criterio.

Corrección:

- el conjunto base son las PlanEvaluation seleccionadas de la ventana;
- contar STABLE únicamente para esas fechas evaluadas;
- una fecha TDEE ajena/no evaluada dentro del mismo span no suma;
- una UNSTABLE ajena/no evaluada tampoco debe bloquear el criterio;
- una evaluación seleccionada que usó estabilidad UNSTABLE sí bloquea.

La forma más directa y fiel es usar:

PlanEvaluation.estimatorStabilityStatus

porque representa el input de estabilidad realmente usado por PlanEvaluator en esa fecha.

Para exponer versiones TDEE, si se usan tdeeEstimates:
- restringirlas a los tdeeEstimateId realmente referenciados por las evaluaciones seleccionadas;
- no usar TDEE ajenos solo porque caen dentro del mismo rango civil.

No inventar métricas faltantes.

Tests obligatorios:

ST-01
6 evaluaciones seleccionadas STABLE + 1 TDEE STABLE no evaluado dentro del span -> sigue siendo 6 / NOT_MET.

ST-02
7 evaluaciones seleccionadas STABLE -> MET si los demás requisitos del criterio están bien.

ST-03
7 evaluaciones seleccionadas STABLE + TDEE UNSTABLE ajeno/no evaluado -> no bloquea.

ST-04
Una evaluación seleccionada con estimatorStabilityStatus=UNSTABLE -> criterio NOT_MET aunque existan >=7 otras STABLE.

4. PROVENIENCIA: IDEMPOTENCIA NO DEBE PERDER UN OBSERVADO PROSPECTIVO REAL
==================================================

Defecto actual:

saveEvaluation retorna inmediatamente cuando:

current.evidenceKey == evaluation.evidenceKey
&& current.inputRevision == evaluation.inputRevision

Eso puede perder una actualización real de procedencia.

Ejemplo:
- existe una fila legacy/null o un backfill false para hoy;
- el usuario pulsa realmente “Evaluar hoy en SHADOW”;
- la evidencia científica es idéntica;
- incoming prospectiveObserved = true;
- el early return conserva null/false y pierde el hecho prospectivo real.

Corrección:

La idempotencia debe separar:

A. evidencia de evaluación;
B. proveniencia de observación.

Si evidenceKey/inputRevision son iguales:

- current=true + incoming cualquier valor -> conservar true, no crear revisión;
- current=null/false + incoming=true -> actualizar la procedencia a true;
- current=null + incoming=false -> puede resolverse estructuralmente a false;
- nunca degradar true a false/null.

Preferencia:

actualizar solo el metadato prospectiveObserved de la fila vigente mediante una operación Room focalizada, SIN crear una revisión artificial y SIN reconstruir DecisionStateMemory, porque la procedencia no altera la decisión.

No cambiar Room v5.
No agregar columna.
No crear tabla.

Tests:

PV-01
Fila legacy null + misma evidence/revision + evaluación prospectiva true -> fila vigente queda true y no aumenta revision/count de filas.

PV-02
Fila false + misma evidence/revision + true -> queda true sin nueva revisión.

PV-03
Fila true + incoming false/null -> permanece true.

PV-04
Misma evidencia/proveniencia ya resuelta -> no-op real.

5. ALTERNANCIAS: RAZONES ESTRUCTURALES VS NUEVA EVIDENCIA
==================================================

Defecto actual:

analyzeTransitions exige simultáneamente:

evidenceKey distinto
Y
inputRevision distinto

para cualquier explicación, incluso POLICY_CHANGED o SAFETY_REVIEW_REQUIRED.

Además DIRECTIONAL_THRESHOLD_MET está en el conjunto genérico de razones justificantes, por lo que una inversión directa ADJUST_DOWN -> ADJUST_UP puede quedar automáticamente justificada simplemente porque el nuevo candidato volvió a cruzar un threshold.

Corrección conservadora:

1. evidenceKey es la identidad canónica. No exigir además inputRevision distinto para reconocer evidencia nueva.

2. Razones estructurales/reset que justifican una transición aunque inputRevision fuente no cambie:
- PLAN_CHANGED;
- POLICY_CHANGED;
- SAFETY_REVIEW_REQUIRED;
- SAFETY_CAUTION;
- TDEE_UNSTABLE;
- TDEE_STABILITY_INSUFFICIENT;
- COOLDOWN_ACTIVE si aparece en el camino.

3. DIRECTIONAL_THRESHOLD_MET por sí sola NO debe ser una explicación estructural suficiente para ocultar una inversión directa.

4. Una transición direccional opuesta puede considerarse explicada por evidencia ordinaria cuando existe un puente no direccional explícito, por ejemplo MAINTAIN/OBSERVE con WITHIN_TOLERANCE, y posteriormente nueva evidenceKey.

5. Si hay ADJUST_DOWN -> ADJUST_UP directa, sin reset/gate estructural ni puente no direccional explicativo, mantenerla como alternancia que requiere revisión/bloqueo conservador aunque exista una nueva lectura.

Tests:

AL-02
SAFETY_REVIEW_REQUIRED con misma inputRevision no se marca injustificada.

AL-03
ADJUST_DOWN -> ADJUST_UP directa con solo DIRECTIONAL_THRESHOLD_MET y nueva evidencia -> sigue siendo injustificada.

AL-04
ADJUST_DOWN -> MAINTAIN(WITHIN_TOLERANCE) -> ADJUST_UP con nueva evidenceKey -> explicada.
